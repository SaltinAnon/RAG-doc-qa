# 星云数据平台 技术架构说明

## 一、总体架构

平台采用微服务架构，按业务域拆分为八个核心服务：

1. **gateway-service**：统一入口，负责鉴权、限流、路由与协议转换。
2. **metadata-service**：元数据管理，维护数据源、表、字段的注册信息。
3. **ingestion-service**：数据接入，负责连接器调度与增量同步。
4. **compute-service**：计算引擎，执行 SQL 与数据加工任务。
5. **query-service**：查询服务，对外提供统一的查询 API。
6. **rag-service**：智能问答服务，实现文档检索与生成。
7. **notification-service**：通知服务，负责邮件、短信、Webhook 推送。
8. **audit-service**：审计服务，记录全部敏感操作。

服务间通过 gRPC 同步调用，通过 Kafka 做异步事件传递。

## 三、RAG 服务详细设计

rag-service 是智能问答的核心，实现路径如下：

1. **文档解析**：支持 PDF、DOCX、Markdown、HTML，使用 pypdf 与 python-docx。
2. **切分策略**：采用递归字符切分，chunk 大小 512 字符，重叠 80 字符。
   中文场景下切分符按"段落 → 句号 → 逗号"的优先级降级。
3. **向量化**：默认使用 BGE-large-zh-v1.5 模型，向量维度 1024。
   高并发场景下可切换为在线 Embedding API。
4. **向量存储**：Milvus 使用 HNSW 索引，参数 M=16、efConstruction=200。
5. **检索策略**：向量检索与 BM25 关键词检索并行执行，
   用 RRF（Reciprocal Rank Fusion）融合，k 值取 60。
6. **重排序**：使用 bge-reranker-base 交叉编码器对 top-20 精排至 top-5。
7. **生成**：调用大模型生成答案，Prompt 中强制要求标注引用编号。

关键性能指标：P99 检索延迟 180 毫秒，端到端问答平均延迟 2.4 秒。

## 四、容量与性能

- 单集群支持 2000 QPS 的元数据查询；
- 数据接入峰值吞吐 每秒 20 万条记录；
- 向量库单集合支持 1 亿条向量，检索召回率 Recall@10 达到 0.96；
- 平台日均处理任务约 45 万个。

## 五、高可用设计

1. 所有无状态服务至少 3 副本，跨可用区部署。
2. 数据库主从切换由 Patroni 自动完成，RTO 小于 30 秒，RPO 接近 0。
3. Kafka 副本因子 3，最小同步副本数 2，保证消息不丢。
4. Redis 集群任一主节点故障时，从节点在 10 秒内自动提升。
5. 全链路设置熔断与降级，网关侧限流阈值默认每服务 1000 QPS。

## 六、安全设计

- 所有服务间调用启用 mTLS 双向认证；
- 数据库连接串通过 Vault 动态下发，有效期 24 小时；
- 敏感字段（手机号、身份证）落库前做 AES-256 加密；
- 生产环境禁止直连，所有运维操作须经跳板机并全程录屏。

## 七、部署与发布

采用 GitOps 流程，所有变更通过 Pull Request 评审后合并。
CI 使用 GitHub Actions 完成构建、单元测试与镜像推送，
CD 使用 ArgoCD 监听镜像仓库，实现声明式自动发布。
发布策略为金丝雀发布，先放量 5%，观察 30 分钟后逐步扩至 100%。

## 八、数据存储与分层

平台采用 Lambda 架构，分为批处理层、速度层与服务层：

1. **批处理层**：基于 Spark 3.5 与 Iceberg 构建，处理 T+1 的全量数据。
   离线任务每日 0:30 启动，SLA 为 6 小时内完成。
2. **速度层**：基于 Flink 1.19 做实时流处理，端到端延迟控制在 3 秒以内。
3. **服务层**：对外提供统一查询入口，查询引擎为 Trino 435，
   在 Iceberg 与 ClickHouse 之间做联邦查询。

数据按「原始层 ODS → 明细层 DWD → 汇总层 DWS → 应用层 ADS」四层建模，
每层之间通过调度系统 DolphinScheduler 编排，日均调度任务约 12 万个。

存储成本控制：ODS 层热数据保留 90 天，超期转入低频存储；
DWD 与 DWS 层采用 ZSTD 压缩，压缩比约为 5:1。

## 九、性能优化实践

- **向量检索优化**：为 Milvus 配置分片（shard_num=4）与分区（按租户分区），
  使单次检索的扫描范围从全量 1 亿条降到单租户的百万量级。
- **缓存策略**：热点查询结果缓存在 Redis，缓存键为查询指纹的哈希，
  命中率约 62%，P99 延迟从 180 毫秒降至 45 毫秒。
- **连接池**：数据库连接池最大 50、最小 10，空闲连接回收时间 300 秒。
- **批量写入**：写入 ClickHouse 采用每批 5000 行、间隔 1 秒的微批策略，
  相比单行写入吞吐提升约 40 倍。

## 十、监控与告警体系

- **指标采集**：Prometheus 每 15 秒抓取一次，共采集 3200 余项指标。
- **日志体系**：ELK 集群，日均写入 800GB，日志保留 30 天。
- **告警分级**：P0（服务不可用）5 分钟内电话告警；P1（功能受损）15 分钟内
  企业微信告警；P2（性能下降）仅记录工单。
- **容量规划**：每月输出容量水位报告，任一资源使用率超过 70% 触发扩容评审。

## 十一、容量与成本

- 生产集群共 24 个 Kubernetes 节点，单节点规格为 32 核 128GB。
- 日均计算资源消耗约 18000 核时，月末结算高峰可达 32000 核时。
- 对象存储总量约 1.2PB，月增长约 40TB。
- 平台整体月度云成本约 86 万元，其中计算占 62%、存储占 28%、网络占 10%。

## 十二、技术债务与改进方向

1. 部分老服务的 Java 版本仍停留在 8，计划在 2026 年底前全部升级到 21。
2. Trino 在跨源联邦查询时的性能不稳定，计划引入物化视图缓存。
3. 向量库的索引重建目前需要停机 20 分钟，计划改造成在线双写切换。
4. 缺少完整的混沌工程演练机制，计划接入 Chaos Mesh 做故障注入测试。

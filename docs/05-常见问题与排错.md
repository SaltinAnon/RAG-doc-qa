## 一、安装阶段

### `ERROR: Could not find a version that satisfies the requirement xxx`

**原因**：Python 版本太新（3.13）或太旧（3.9 以下），没有对应的预编译 wheel。

**解决**：

```bash
python --version       # 必须是 3.11 或 3.12
```

用 3.12 重建虚拟环境：

```bash
rm -rf .venv                                  # Windows: rmdir /s /q .venv
D:\Python\python.exe -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

### 装依赖卡在 `Installing build dependencies` 很久

**原因**：pip 在从源码编译某个包（通常是 `chroma-hnswlib`、`onnxruntime`）。

**解决**：

1. 先耐心等 5~10 分钟（编译确实慢）；
2. 换个镜像源试试：
   ```bash
   pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
   ```
3. 确认 Python 是 3.12（3.13 上很多包只有源码没有 wheel）。

### pip 解析依赖卡住不动

**原因**：pinned 版本太多时，pip 的 backtracking 解析器可能陷入长循环。

**解决**：

```bash
# 让 pip 用更长超时、更激进的重试
pip install -r requirements.txt --timeout 120 --retries 5 -i https://mirrors.aliyun.com/pypi/simple/
```

如果还是不行，可以分两批装：

```bash
pip install fastapi uvicorn python-multipart pydantic pydantic-settings
pip install langchain langchain-core langchain-community langchain-openai langchain-chroma langchain-text-splitters chromadb
pip install pypdf python-docx rank-bm25 numpy streamlit requests httpx tenacity tiktoken pytest
```

## 二、启动阶段

### `ModuleNotFoundError: No module named 'app'`

**原因**：不在项目根目录执行命令。

**解决**：

```bash
cd F:/WorkSpace/Newstart      # 必须是这里
.venv\Scripts\python.exe -m uvicorn app.main:app --port 8000
```

### `ModuleNotFoundError: No module named 'langchain'`

**原因**：用了系统 Python 而不是虚拟环境的 Python。

**解决**：用完整路径 `.venv\Scripts\python.exe`，不要直接敲 `python`。

先确认依赖装在哪：

```bash
.venv\Scripts\python.exe -c "import langchain; print(langchain.__version__)"
```

### 端口被占用 `[Errno 10048] error while attempting to bind on address`

**九成情况是：你上次启动的服务根本没关。**（后台窗口一关、终端一叉，进程往往还在跑）

#### 第一步：先确认到底有没有在跑（只看 LISTENING）

```bash
# Windows（Git Bash / CMD 都可以）
netstat -ano | findstr :8000          # 看 STATE 是 LISTENING 的那一行，记下最后一列 PID
tasklist | findstr python             # 看有哪些 python 进程
```

```bash
# macOS / Linux
lsof -i :8000
```

> ⚠️ 只看 `LISTENING` 的行。如果只看到 `TIME_WAIT`，**那不是没关掉** ——
> 它是连接关闭后客户端侧的正常 TCP 收尾状态，**会自动消失（约 30~120 秒）**，
> 也**不会**阻止你重新绑定端口。看到 `TIME_WAIT` 不用管。

#### 第二步：确认这个 PID 是你自己的服务再杀

```bash
# 先看清命令行，别误杀别的 python
wmic process where "ProcessId=<PID>" get CommandLine     # Windows
ps -p <PID> -o command                                   # macOS / Linux
```

确认是本项目的 uvicorn 之后再结束它：

```bash
taskkill /PID <PID> /F      # Windows
kill <PID>                  # macOS / Linux（加 -9 强制）
```

**一条命令直接找 uvicorn 并全部结束**（确认过都是本项目的再用）：

```bash
# Windows PowerShell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Where-Object { $_.CommandLine -like "*uvicorn*" } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

#### 第三步（推荐）：以后根本别手工起服务

手工「起服务 → curl → 关服务」的翻车点不止「忘了关」一个，
最容易骗到自己的是：**你以为测的是新代码，其实打到的是上一版没死的进程上。**

这个项目提供了自包含的冒烟脚本，**用 `try/finally` 保证服务一定被关掉**：

```bash
make smoke                                  # 或
.venv\Scripts\python.exe scripts/smoke_test.py
```

它会：自动起服务 → 轮询 `/healthz` → 跑「能答的必须答、不能答的必须拒答」
共 14 项断言 → **无论成败都关闭服务** → 全通过时顺手清掉日志。

```bash
# 端口被占时换个端口跑
.venv\Scripts\python.exe scripts/smoke_test.py --port 18123

# 调错时保留服务，脚本会把该杀哪个 PID 直接告诉你
.venv\Scripts\python.exe scripts/smoke_test.py --keep
```

退出码 0/1，可以直接挂进 CI。

> 💡 通用习惯：**只要你在脚本/终端里 `&` 起了一个长驻进程，
> 就在同一个脚本里写一个 `finally` 把它关掉。**
> 「我会记得手动关」是靠不住的 —— 记忆不是可靠性机制，`finally` 才是。


### 启动日志里出现 `⚠️ API_KEY 为空，接口鉴权已关闭`

**这不是错误**，是提醒。本地开发本来就不该开鉴权。
但**部署到公网前必须设置**，否则任何人都能上传文档并消耗你的模型额度。

```ini
# .env
API_KEY=一个足够长的随机字符串
```

设置后前端侧边栏要填同样的值。

## 三、入库阶段

### 上传 PDF 报「提取不到任何文本」

**原因**：**扫描版 PDF**（内容是图片，没有文本层）。pypdf 只能读文本层。

**解决**：

```bash
# 用 ocrmypdf 加一层文本（需要先装 tesseract + 中文语言包）
pip install ocrmypdf
ocrmypdf -l chi_sim 扫描件.pdf 输出.pdf
```

或者用 WPS / 微信「提取文字」功能先转成文本再上传。

> 本系统**故意**不集成 OCR：会额外增加 500MB~1GB 镜像体积，
> 而扫描件在企业文档里占比不高，给出明确指引更划算。
> 这是有意的取舍，不是遗漏（已写进 README 的「已知限制」）。

### `ChromaDB 初始化失败` / `database is locked`

**原因**：并发写入冲突，或有另一个进程正在使用同一个向量库目录。

**解决**：

1. 确认没有第二个服务实例在跑（检查任务管理器里的 python 进程）；
2. 本项目已经用单例 + 写锁做了串行化，如果你改了代码引入多进程，需要改用独立集合或换 Milvus。

### `documents(x) 与 embeddings(x) 数量不一致`

**原因**：向量化过程中丢数据了。通常是 Embedding API 批量调用的返回条数不足。

**解决**：检查 `.env` 里的 `EMBEDDING_BATCH_SIZE`，调小（比如 16）再试。

### 入库报错 `docs 数量不匹配` / 维度不一致

**症状**：`Collection expecting embedding with dimension of 512, got 1536`

**原因**：**换了 Embedding 模型但没重建向量库**。
不同模型的向量维度不同，同一个 Chroma 集合里不能混用。

**解决**：

```bash
# 清空集合后重新入库
.venv\Scripts\python.exe scripts/ingest_cli.py --dir data/docs --reset

# 或者干脆删掉整个向量库目录
rm -rf data/chroma
```

### `切分文档「xxx」失败：切分后没有任何有效片段`

**原因**：文档太短，或者内容全是符号/表格线，被噪声过滤器全滤掉了。

**解决**：

```bash
# 先预演看看切分情况
.venv\Scripts\python.exe scripts/ingest_cli.py --dir data/docs --dry-run

# 如果是短文档，调小 chunk_size
# .env:
CHUNK_SIZE=200
CHUNK_OVERLAP=30
```

## 四、问答阶段

### `/query` 返回 503「集合中没有任何文档」

**原因**：知识库是空的。

**解决**：

```bash
.venv\Scripts\python.exe scripts/make_sample_docs.py
.venv\Scripts\python.exe scripts/ingest_cli.py --dir data/docs

# 确认
curl http://localhost:8000/api/v1/documents
```

### 答案前面有「（离线抽取模式·未调用大模型）」

**这不是 bug**，是设计如此：没有配置 LLM API Key。

**解决**：在 `.env` 里填 `LLM_API_KEY`，重启后端。

```ini
LLM_PROVIDER=deepseek
LLM_MODEL=deepseek-chat
LLM_API_KEY=sk-xxxxx
```

### 答案说「根据现有资料无法回答该问题」，但知识库里明明有

**先看一个字段，再去猜原因**：响应里的 `refusal_reason` 会直接告诉你卡在哪一步。

| `refusal_reason` | 含义 | 该查什么 |
|---|---|---|
| `no_retrieval` | 检索阶段一无所获 | 文档是否入库、向量维度是否漂移 |
| `model_refused` | 检索到了片段，但判定资料不足 | 换用文档原词提问；或看下面的排查顺序 |
| `empty_output` | 模型返回了空串（异常） | 模型/网关问题，看服务端日志里的 `模型返回空答案` |

> 别去匹配 `answer` 里的文字判断是不是拒答 —— 直接读 `refused` 字段。
> 文案是会改的，字段不会。

**可能原因与排查顺序**：

1. **文档没入库成功**
   ```bash
   curl http://localhost:8000/api/v1/documents
   ```
2. **问题用词与文档差异过大**
   先用文档里的原词试试。如果原词能答出来、换个说法就不行，
   说明 Embedding 的语义泛化能力不足（`hash` 模式就是这样，正常）。
3. **检索参数不合适**
   把 `top_k` 调大（侧边栏滑块，或 `.env` 的 `TOP_K=8`）。
4. **看检索调试信息**
   展开界面上的「🔬 检索调试信息」：
   - `vector_hits = 0` → 向量库有问题
   - `vector_hits > 0` 但 `fused = 0` → 融合环节有问题
   - `fused > 0` 但答案还是拒答 → 离线相关度闸门判的，跑
     `python scripts/calibrate_gate.py` 看阈值分布
5. **拒答却带着引用 / 该拒答却答了**
   `refused=true` 时 `citations` 应当为空。若不为空，说明
   `chain.answer()` 里「拒答不挂引用」那条分支被绕过了。

### 引用编号和正文对不上

**原因**：这是 RAG 最典型的 bug，说明 `format_context()` 的编号
与 `_build_citations()` 的回查逻辑不一致。

**排查**：

```python
# 打印一下编号映射
from app.core.prompts import format_context
text, indexed = format_context(docs)
print(text[:500])
print([(i, d.metadata["source"]) for i, d in indexed])
```

本项目有专门的单元测试保护这一点：
`tests/test_llm_offline.py::TestFormatContext::test_index_matches_document_order`。
如果你改了 Prompt 模板，先跑一遍这个测试。

### 答案没有引用（citations 是空数组）

**排查**：正常情况下 `_build_citations()` 有兜底，不会返回空。
如果真的是空的，说明 `format_context()` 返回的 `indexed` 是空的
——也就是检索结果为空，但 `is_empty()` 判断没拦住。

**检查**：`.env` 里的 `SCORE_THRESHOLD` 是否设得太高。

### ⭐⭐ 报 `APIConnectionError: Connection error.`（网络层到不了 API）

**症状**：`.env` 里 provider / model / key 全都配对了，仍然报
`APIConnectionError: Connection error.`，而且**填不填 `LLM_BASE_URL` 都一样**。

**先记住一条**：这个错误**不是配置问题，是网络到不了**。
所以别再去改 `LLM_MODEL` 或 `LLM_API_KEY` 了，那些都不会有用。

**头号元凶：进程里有代理环境变量。**

很多人机器上装了代理软件（Clash / v2ray / 公司代理），或者某个工具往环境变量里
写了代理地址 —— Python 进程会**自动继承**它，于是请求被导到一个不通的代理上。

**一步诊断**（把每一层都实测一遍，直接告诉你是哪层的问题）：

```bash
python scripts/doctor.py
```

输出形如：

```
  ✅ 模型名检查        'deepseek-chat' 看起来正常
  ❌ 代理环境变量      HTTPS_PROXY=http://127.0.0.1:57079（代理端口 127.0.0.1:57079 连不上 ❌）
  ✅ API 地址          https://api.deepseek.com/v1
  ✅ DNS 解析 api.deepseek.com   → 120.221.61.47（5 ms）
  ✅ TCP 连接         已连通（41 ms）
  ✅ HTTPS 握手        成功（TLSv1.3）
结论：❌ 发现 1 个问题：代理环境变量
建议：⭐ 最可能的原因：检测到不可用的代理且请求会走代理……
```

也可以直接问接口（服务已启动时）：

```bash
curl "http://localhost:8000/doctor?network=false"
```

**确认是不是代理在捣乱**（Windows PowerShell，在当前终端执行后再启动服务）：

```powershell
$env:HTTP_PROXY=""; $env:HTTPS_PROXY=""; $env:ALL_PROXY=""
python -m uvicorn app.main:app --reload
```

如果这样就好了 → 就是代理的问题。

**永久解决**，三选一：

1. **让 API 域名绕过代理**（推荐，不影响你其它软件用代理）：
   ```powershell
   $env:NO_PROXY="api.deepseek.com,api.openai.com,open.bigmodel.cn,api.moonshot.cn"
   ```
2. 启动脚本里显式清空代理变量（上面那行 `$env:...=""`）。
3. 关掉那个代理软件，或把它设为「直连」。

**如果 `doctor.py` 显示 DNS / TCP / HTTPS 有 ❌**：

| 失败项 | 含义 | 怎么办 |
|---|---|---|
| DNS 解析失败 | 域名解析不了 | 换 DNS、检查网络，试试**手机热点** |
| TCP 连接失败 | 443 端口不通 | 公司网络 / 防火墙拦截；换网络环境 |
| HTTPS 握手失败 | 证书校验不过 | 通常是公司中间人代理或系统时间不对 |

> 💡 **一个重要的排查原则**：
> **「填了 base_url 就能用」并不代表 base_url 的默认值有 bug。**
> 本项目在修复后，留空和显式填写**发出的请求完全相同**（都是 `CONNECT api.deepseek.com:443`），
> 有实测抓包为证。判断配置问题要看**实际生效的值**（`doctor.py` 或 `/readyz`），
> 不要靠「改了某个值就好了」这种相关性来下结论 —— 那很可能只是**幸存者偏差**。

#### ⚠️ 代理环境变量的**大小写**在 Windows / Linux 上是两回事

写脚本或排查时**必须注意**这个平台差异（本项目踩过一次，本地绿、Linux CI 红）：

| | `HTTP_PROXY` 与 `http_proxy` |
|---|---|
| **Windows** | **同一个**变量（`os.environ` 大小写不敏感）—— 设小写也能被大写名读到 |
| **Linux / macOS** | **两个不同**变量（严格区分大小写）—— 只设小写，用大写名**读不到** |

后果：如果检测代码只查大写名 `os.environ.get("HTTPS_PROXY")`，
在 Windows 上「碰巧能用」，到了 Linux 上**小写配置的代理会被完全漏检** ——
`doctor.py` 说「没检测到代理」，用户却一直连不上。

正确做法是**遍历环境里真实存在的键**、按大写归一去重
（见 `app/utils/netcheck.detect_proxies()`），这样两个平台行为一致。
本项目的 `tests/test_netcheck.py` 里有一条**在任意平台都强制按「区分大小写」跑**的回归测试，
专门锁死这个坑。

### ⭐ 配好了 API 还是报 500（最常见：`LLM_MODEL` 没跟着 `LLM_PROVIDER` 改）

**症状**：`.env` 里填了 `LLM_PROVIDER=deepseek` 和 `LLM_API_KEY`，
提问却返回 **HTTP 500**，响应体只有一句「服务器内部错误」。

**原因**：`.env` 里的 `LLM_MODEL` 还是默认的 `gpt-4o-mini`。
程序于是拿 **OpenAI 的模型名**去请求 **DeepSeek 的地址** ——
DeepSeek 上根本没有这个模型，返回 400，最后被包成 500。

> 这是**真实踩过的坑**。注意特征：报 500 而不是 401/404，
> 因为异常在链路里被统一包装了，真正的原因只写在服务端日志里。

**一步定位**（把「配置的」和「实际发出去的」摆在一起看）：

```bash
curl http://localhost:8000/readyz
```

返回里会直接写明：

```json
{
  "llm_provider": "deepseek",
  "llm_model_configured": "gpt-4o-mini",      ← 你 .env 里写的
  "llm_model_effective": "deepseek-chat",     ← 实际会发出去的
  "llm_base_url": "https://api.deepseek.com/v1",
  "llm_config_ok": false,
  "llm_config_warnings": ["LLM_MODEL='gpt-4o-mini' 看起来不属于 provider='deepseek'…"]
}
```

**解决**：把三个变量**成套**改对（`.env` 里这三行是一组）：

```ini
LLM_PROVIDER=deepseek
LLM_MODEL=deepseek-chat          # ← 关键：不能留着 gpt-4o-mini
LLM_API_KEY=sk-你的key
```

> 💡 **更省事的做法**：把 `LLM_MODEL` **留空**。
> 留空时程序会按 `LLM_PROVIDER` 自动选默认模型，从根上不会配错：
> `deepseek → deepseek-chat`、`zhipu → glm-4-flash`、`moonshot → moonshot-v1-8k`。

**各家对照表**（改 provider 时照着换）：

| Provider | `LLM_MODEL` | `LLM_API_KEY` 长什么样 |
|---|---|---|
| `openai` | `gpt-4o-mini` | `sk-...` |
| `deepseek` | `deepseek-chat` 或 `deepseek-reasoner` | `sk-...` |
| `zhipu` | `glm-4-flash` | `xxx.xxx`（形如 `id.secret`） |
| `moonshot` | `moonshot-v1-8k` | `sk-...` |
| `ollama` | `qwen2.5:7b`（本地模型名） | 随便填，如 `ollama` |

**顺带确认 base_url 的两种情况**：

- **留空**（推荐）：按 provider 自动取默认值，不必手填；
- **手填**：多数提供商要带 `/v1` 后缀。
  DeepSeek 是 `https://api.deepseek.com/v1`，
  智谱是 `https://open.bigmodel.cn/api/paas/v4`（这个**不是** `/v1`，别改）。

> ⚠️ 一个容易误判的现象：**「手填了 base_url 就能用了」并不说明 base_url 的默认值有 bug**。
> 手填时人往往会顺手把 `LLM_MODEL` 也一起改对；
> 或者填的是一个**会做模型映射的第三方中转站**，它把 `gpt-4o-mini` 兜住了。
> 真正的判据是看 `/readyz` 里的 `llm_model_effective`，而不是「有没有手填」。

### LLM 调用报错 `401 Unauthorized` / `insufficient_quota`

- `401`：API Key 错了、过期了，**或者根本不是这一家的 Key**
  （DeepSeek 和 OpenAI 的 Key 不通用，这是最容易犯的错）
- `insufficient_quota`：额度用尽

**快速验证 Key 是否有效**：

```bash
curl https://api.deepseek.com/v1/models -H "Authorization: Bearer sk-你的key"
```

> 现在 401/404/400/429/超时 都会被翻译成中文建议，
> 直接告诉你该改 `.env` 的哪一行，不再只给一个 500。

### 生成很慢（十几秒）

**原因**：在线 LLM 首字延迟 + 多轮场景下的查询改写（多一次调用）。

**优化方向**：

1. 换更快的模型（`glm-4-flash`、`qwen-turbo`）；
2. 关掉查询改写（多轮问答会快一点）：
   ```python
   chain.answer(question, enable_rewrite=False)
   ```
3. `FETCH_K` 从 20 调到 10（减少重排计算量）。

### 提问后消息重复出现

这个 bug 已经在开发阶段修复。
如果你自己改前端时又出现了，检查是否在 `st.rerun()` 前后重复渲染了消息。

**正确模式**：

```python
# 实时生成的内容只在当前帧渲染一次
with st.chat_message("assistant"):
    st.markdown(data["answer"])
# 然后 append 并 rerun，交给历史渲染逻辑统一处理
st.session_state.messages.append({...})
st.rerun()
```

## 七、Docker 阶段

### 构建后容器里 data/docs 是空的

**原因**：`.dockerignore` 里排除了 `*.md`，把示例 Markdown 文档一起排除了。

**解决**：这是本项目的真实踩坑。
确认 `.dockerignore` 里没有 `*.md` 这种通配符规则。

### 容器起来了但 `curl /readyz` 返回 `chroma_ok: false`

**排查**：

```bash
docker logs rag-api
```

常见原因：挂载卷的权限问题。Dockerfile 里用的是非 root 用户 `appuser`，
如果宿主机挂载目录属于 root，容器内写不进去。

**解决**：

```bash
# 给挂载目录放开权限（Linux）
sudo chown -R 1000:1000 ./data/chroma
```

### 前端容器连不上后端

**解决**：容器内要用**服务名**而不是 localhost：

```yaml
environment:
  RAG_API_BASE: http://api:8000      # ✅ 用服务名
  # RAG_API_BASE: http://localhost:8000   ❌ 容器内的 localhost 是它自己
```

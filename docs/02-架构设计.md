# 02 · 架构设计

> 本文解释**为什么这么设计**，而不是重复代码里已经有的注释。
> 面试时被问「你这个架构是怎么考虑的」，照着这份文档讲就够了。

## 1. 分层与依赖方向

```
        ┌──────────────────────────────────────┐
        │  frontend/   Streamlit               │  只管展示，通过 HTTP 调后端
        └───────────────┬──────────────────────┘
                        │ HTTP + JSON
        ┌───────────────▼──────────────────────┐
        │  app/api/   路由层                    │  只管协议：解析请求、调用服务、包装响应
        │  app/models/schemas.py 数据契约        │
        └───────────────┬──────────────────────┘
                        │ 直接调用（进程内）
        ┌───────────────▼──────────────────────┐
        │  app/core/   业务核心层                │  只管业务：加载、切分、检索、生成
        └───────────────┬──────────────────────┘
                        │
        ┌───────────────▼──────────────────────┐
        │  app/config.py + app/utils/            │  横向能力：配置、日志、文本工具
        └──────────────────────────────────────┘
```

**依赖方向严格单向向下**，没有反向依赖。这条约束带来三个好处：

1. 改前端不用碰后端（前端只依赖 HTTP 契约，不 import 任何 `app.*`）；
2. 改业务逻辑不用碰路由（路由是薄薄一层协议转换）；
3. 每一层都能单独测试（`tests/` 里既有纯函数单测，也有 TestClient 接口测试）。

### 唯一一处「跨层」的特例

`app/main.py` 的 `/readyz` 里直接 import 了 `app.core.vectorstore`。
这是有意为之：就绪探针需要探测依赖状态，属于运维关注点，
不适合塞进业务层。代码里写了注释说明。

## 2. 写路径（入库）

```
文件 ──► loaders ──► splitter ──► embeddings ──► vectorstore
         解析        切分+去重      向量化         落盘
         ↓             ↓             ↓              ↓
      Document      Document      向量列表      ChromaDB
      (含页码)      (含chunk_id)                (持久化)
```

### 2.1 loaders：为什么自己写

评估过 `langchain_community` 的 `PyPDFLoader` / `Docx2txtLoader` /
`UnstructuredWordDocumentLoader`，不用的原因：

| 问题 | 说明 |
|---|---|
| 额外重依赖 | `UnstructuredWordDocumentLoader` 会拖进 `unstructured` + `nltk`，光词表几十 MB |
| 元数据不可控 | 我们需要精确的「页码」，用于引用溯源；community loader 的 page 语义不明确 |
| 表格处理 | 企业文档的关键信息（报销标准表、数据分级表）在表格里，默认 loader 容易漏 |

**但输出的仍然是 LangChain `Document`**，所以下游的切分器、向量库、链完全不受影响。
这是「自己实现但保持生态兼容」的典型做法。

每个 Document 带这些元数据：

| 字段 | 用途 |
|---|---|
| `doc_id` | 全文内容哈希，用于幂等去重与文档管理 |
| `source` | 原始文件名，展示在引用里 |
| `source_type` | pdf / docx / txt / md，用于统计与差异化处理 |
| `page` | 页码或段号（从 1 开始），引用溯源的核心 |
| `file_hash` | 文件字节哈希，用于判断文件是否被改过 |

### 2.2 splitter：中文三级切分

```
优先级 1：段落级      "\n\n"  "\n"
优先级 2：中文句末    "。" "！" "？" "；"    +  ". " "! " "? " "; "
优先级 3：中文子句    "，" "、"  +  ", " " "
兜底：                ""（硬切）
```

三个关键实现细节：

1. **中文标点必须显式列出**。Python 的 `str.split` 不会把「，」当成「,」，
   照抄英文教程的 separators 会导致中文段落被硬切。
2. **`keep_separator=True`**。否则句末标点会被吃掉，
   相邻 chunk 拼回上下文时句子会黏在一起。
3. **`add_start_index=True`**。记录每个 chunk 在合并文本中的偏移量，
   配合 `page_map` 反查页码。

跨页拼接的设计：

```
页1文本 ─┐
         ├─► 用 "\n\n" 拼接成 merged_text ──► 切分 ──► 按 offset 反查页码
页2文本 ─┘        ↑
                page_map = [(起始偏移, 结束偏移, 页码), ...]
```

为什么必须拼接后再切：**PDF 的分页是排版行为，不是语义边界**。
一句话经常跨页，单独切每一页会把句子切成两半。

### 2.3 splitter 的两道清洗

| 环节 | 目的 | 方法 |
|---|---|---|
| 噪声过滤 | 去掉页眉页脚、纯符号、目录省略号 | 有效字符数 + 有意义字符占比双重判定 |
| 近似去重 | 去掉每页重复的页眉 | 字符 bigram 集合的 Jaccard 相似度 > 0.85 判为重复 |

> 为什么必须有去重：不去重的话，top-5 检索结果可能 3 条都是同一句页眉，
> 白白浪费上下文窗口，还让 LLM 以为「多处都这么说」。

### 2.4 vectorstore：三个关键点

1. **用 `upsert` 而不是 `add`**。`add` 遇到重复 ID 会抛异常；
   我们的 `chunk_id` 是内容哈希，同一文档重复上传时 ID 相同，
   `upsert` 天然幂等。
2. **显式指定余弦距离**。Chroma 默认是 L2 欧氏距离，
   对文本向量余弦更合适，而且 `1 - cos` 可以直接转成「相似度」展示。
3. **分批写入（每批 1000）**。Chroma 底层是 SQLite，
   单次写入受变量数量上限约束（约 5461），**超过后静默部分写入**。
   这个坑只有做写入后数量核对才能发现。

## 3. ⭐ 双后端设计（本项目最重要的工程决策）

### 问题

一个「没 API Key 就跑不起来」的项目，在 GitHub 上是劝退的。
评分和复现都会挂，简历项目反而变成减分项。

### 方案

`embeddings.py` 和 `llm.py` 都实现**工厂 + 自动降级**：

```
get_embeddings(provider)
   ├─ "openai" ──► OpenAIEmbeddings        （有 Key 时最好）
   ├─ "local"  ──► HuggingFaceEmbeddings   （BGE-small-zh，免费离线）
   └─ "hash"   ──► LocalHashEmbeddings     （纯 Python，零依赖）
        ↑ 前两者任一初始化失败，都自动落到这里

get_llm()
   ├─ 在线 ──► ChatOpenAI（任意 OpenAI 兼容端点）
   └─ 离线 ──► ExtractiveLLM（从参考资料抽取句子拼答案）
        ↑ 没 Key / 包没装 / base_url 写错，自动落到这里
```

### 三条铁律（写进了 CLAUDE.md）

1. **降级必须显式暴露**——API 响应里 `offline_mode: true`，
   `model` 字段写 `offline-extractive`，答案第一行带标记，前端顶部显示黄条。
   **绝不静默假装是 AI 生成的答案。**
2. **降级只影响「生成质量」，不影响链路正确性**——检索、引用溯源、
   接口鉴权、会话记忆全都在正常工作。
3. **所有降级逻辑必须被 pytest 覆盖**——这是 CI 能完全离线的根本原因。

### 拒答也要是一个字段（`refused`）

「答不上来」是一种**结果状态**，必须结构化暴露，而不是靠上层去猜文案：

| 字段 | 含义 |
|---|---|
| `refused: bool` | true 表示系统判定无法回答，未编造答案 |
| `refusal_reason` | `no_retrieval` / `model_refused` / `empty_output` |

约定：**`refused=true` 时 `citations` 恒为空**。拒答却挂着引用，等于给一个
「答不上来」的结果伪造了依据，比不返回引用更糟。

识别逻辑集中在 `prompts.is_refusal_text()`，只认 Prompt 契约里约定过的固定话术
（`根据现有知识库无法回答` / `根据现有资料无法回答` / `无法根据现有资料`），
**绝不放进「没有」「不知道」这类会误伤的通用词**。
这正是「拒答准确率」这个指标可信的前提。

### LocalHashEmbeddings 的算法（面试可深挖）

```
文本
 ├─ 抽字符 n-gram：中文 unigram(权重1.0) + bigram(2.0) + trigram(1.5)
 │                英文整词(2.0)
 │   ↑ bigram 权重最高：中文里双字词是最强语义单元
 │     （「年假」vs「假年」完全不同；单看「假」字没有信息）
 │
 ├─ signed hashing：blake2b(ngram) → 前4字节取桶索引，第5字节奇偶决定 ±1
 │   ↑ 带符号让不同 token 的哈希碰撞互相抵消，而不是无限累加噪声
 │
 ├─ 次线性词频压缩：1 + log(tf)   ← 避免高频词支配向量
 │
 └─ L2 归一化 → 余弦相似度 = 点积
```

**关键实现约束**：必须用 `hashlib.blake2b`，**不能用 Python 内置 `hash()`**。
内置 `hash()` 对字符串按进程随机加盐（`PYTHONHASHSEED`），
服务重启后同一文本得到完全不同的向量，会让幂等入库彻底失效。

**已知局限（写在代码注释里，不藏着）**：
它不理解语义（「年假」和「带薪休假」在这套表示下几乎不相关），
但字面精确匹配很强，对专有名词/编号反而比小模型更靠谱。
所以它是**兜底**，不是效果方案。

## 4. 读路径（检索）

```
query
  │
  ├─[可选] 查询改写：结合历史把指代词还原成实体（仅在线模式）
  │
  ├─ 向量检索 ──► fetch_k=20 条 (Document, 余弦相似度)
  ├─ BM25 检索 ─► fetch_k=20 条 (Document, BM25 分)    ← 并行两路
  │
  ├─ RRF 融合
  │     score(d) = Σ_r 1 / (60 + rank_r(d))
  │     归一化分母 = 2/(60+1)（两路都排第一的理论最大值）
  │
  ├─ 启发式重排
  │     0.40 × 查询词覆盖率
  │   + 0.25 × 短语命中率
  │   + 0.20 × 数字/编号命中
  │   + 0.15 × 长度合理性
  │     最终分 = 0.4 × RRF + 0.6 × rerank
  │
  ├─ 相似去重（剔除相邻 chunk 的 85% 重叠，MMR 简化版）
  │
  └─ 截断到 top_k
```

### 4.1 为什么必须混合检索

向量检索擅长**语义相似**，但对精确字面匹配不敏感：

| 用户问 | 向量检索 | BM25 |
|---|---|---|
| 「年假几天」→ 文档写「带薪年休假 5 天」 | ✅ 语义命中 | ❌ 字面不重叠 |
| 「GB/T 19001 是什么」→ 文档有该编号 | ❌ 编号被「平均」掉 | ✅ 精确命中 |
| 「张三的入职日期」→ 文档有「张三」 | ⚠️ 人名被弱化 | ✅ 精确命中 |

### 4.2 为什么用 RRF 而不是加权平均

两种检索器的分数**量纲不同**（余弦 0~1 vs BM25 无上界），
`0.5*v + 0.5*b` 是错的——权重永远调不好，换个数据集就得重调。

RRF 只用**排名**不用分数：

| 特性 | 收益 |
|---|---|
| 无量纲 | 不用归一化、不用调参 |
| 鲁棒 | 某一路出现异常大分数也不会带偏结果 |
| 奖励共识 | 两路都排第 3 的文档 > 一路第 1、另一路第 50 的文档 |

`k=60` 的作用是压低「排第 1」的过度优势。这个值来自原论文，是经验值。

### 4.3 重排序为什么用启发式

生产环境这里应该用 Cross-Encoder（如 `bge-reranker-base`），
但那个要额外 400MB 依赖。本项目的取舍是：

> **用 10 行代码拿到重排 80% 的收益，同时保留替换接口。**

`_rerank()` 是独立静态方法，换成模型重排只需改这一个方法。

长度打分曲线（抽成独立方法，可以直接对曲线本身写单测）：

```
ratio = 片段长度 / CHUNK_SIZE
  ratio < 0.2   → 0.20      极短碎片，强烈惩罚
  0.2 ~ 0.5     → 线性升到 1.0
  0.5 ~ 1.5     → 1.00      甜区
  > 1.5         → 缓慢衰减到 0.3
```

### 4.4 BM25 的缓存策略

`BM25Okapi` 每次构造都要遍历全库做词频统计，3000 条 chunk 要 600ms。

缓存键 = `(集合名, chunk 数量)`。数量变了才重建。
用数量而不是哈希，是因为它 O(1) 且足够灵敏——入库必然改变数量。

效果：单次检索从 600ms 回到 45ms。

## 5. 引用溯源链路

这是整个项目**最有含金量的部分**，也是面试最容易被追问的。

```
       ① 编号化                     ② 强制引用
检索片段 ──────► Prompt 里 [1] [2] [3] ──────► 模型输出带 [n] 的答案
                                                        │
                        ┌───────────────────────────────┘
                        ▼
       ③ 解析                ④ 回查                ⑤ 兜底
正则 \[(\d{1,2})\]  ──►  按编号取 Document  ──►  模型漏标时挂 top-3
                         提取 source/page/         并标记 fallback=true
                         snippet/score
```

### 为什么需要第 ⑤ 步

小模型经常忘记标引用。如果不做兜底：
- 要么返回空引用列表（接口层面「没有溯源」，卖点失效）；
- 要么硬塞一个假引用（更糟，是编造）。

正确的做法是：**挂上真实检索到的片段，但在调试信息里记录
「这是兜底的不是模型主动标的」**。这样既不隐瞒，又保证可用性。

### 编号错位是 RAG 最常见的 bug

`format_context()` 的编号必须与最终 `citations` 里的 `index` 严格对应。
一旦错位，用户点开引用看到的原文和答案对不上，整个溯源功能就成了负资产。

所以 `tests/test_llm_offline.py::TestFormatContext::test_index_matches_document_order`
专门测这一点。

## 6. 会话记忆设计

```python
class SessionMemory:
    _sessions: dict[str, _Session]   # session_id → 会话状态
    _lock: threading.Lock            # FastAPI 是多线程的，字典操作必须加锁
```

三个定制行为：

| 特性 | 为什么需要 |
|---|---|
| 按 `session_id` 隔离 | 不同用户的对话不能串 |
| 轮数上限（默认 6） | 否则 prompt 无限膨胀直到超长报错 |
| TTL 过期（默认 120 分钟） | **否则长跑服务会内存泄漏**——这是真实的生产问题 |

### 为什么不用 LangChain 的 ConversationBufferMemory

`ConversationBufferMemory` 在 LangChain 0.3 已 **deprecated**，
官方推荐 `RunnableWithMessageHistory`。但我们两个都没用：

1. `RunnableWithMessageHistory` 要求链的第一个节点接受 **message 列表**，
   而我们的离线降级 `ExtractiveLLM` 是 `LLM`（文本进文本出），
   接上去会直接报类型错误；
2. 我们需要「隔离 + TTL + 轮数上限」三点定制，LangChain 内置的要额外包一层。

> 迁移路径：只要换回 `ChatModel`，链结构一行不用改。

### 查询改写

多轮场景下的真实问题：

```
第1轮：「公司的年假有多少天？」  → 检索「年假」✅
第2轮：「那病假呢？」           → 检索「那病假呢」❌（「那」「呢」是噪声）
```

做法：让 LLM 结合历史把「那病假呢」改写成「公司的病假有多少天？」再检索。

**关键工程约束**：改写失败必须**静默回退到原问题**。
可选增强功能绝不能拖垮主链路的可用性。这条后来成了项目的通用原则。

## 7. Prompt 工程

集中在 `app/core/prompts.py`，带 `PROMPT_VERSION` 便于定位问题。

四条硬规则：

| 规则 | 目的 | 违反后果 |
|---|---|---|
| 只允许依据参考资料回答 | 抑制幻觉 | 模型用预训练知识编答案，引用对不上 |
| 每个事实性陈述必须带 `[n]` | 可溯源 | 无法验证，项目卖点全失 |
| 资料不足必须明说「无法回答」 | 诚实拒答 | 强行编一个看似合理的答案 |
| 引用编号必须与给定编号一致 | 绑定正确 | 引用张冠李戴 |

两条中文特有经验：

- **用「参考资料」而不是「上下文」**：中文模型对「上下文」的理解偏向
  对话历史，会把用户前几轮说的话当成可引用材料，导致编号错位。
- **显式约束输出语言**：混排场景（中文问、英文文档）下模型容易
  跟随文档语言作答。

## 8. 可观测性

| 手段 | 实现 |
|---|---|
| 请求 ID | 中间件生成 8 位 ID，写入日志 `rid=` 字段与响应头 `X-Request-ID` |
| 耗时统计 | 响应头 `X-Process-Time-Ms`；`try/finally` 保证异常路径也记录 |
| 检索调试 | 响应里的 `retrieval_debug`：各阶段命中数 + `citation_fallback`（引用是否为兜底挂上） |
| 降级状态 | `/readyz` 与 `/config/status` 暴露 `llm_offline` |
| 拒答状态 | `/query` 响应里的 `refused` / `refusal_reason`（见 §「拒答也要是一个字段」） |
| 结构化日志 | `logger.info("入库完成 file=%s chunks=%d", ...)` 而不是 f-string |

> 为什么日志用 `%s` 占位而不是 f-string：
> f-string 会**无条件**求值（哪怕日志级别不输出），
> 在热路径上白做字符串拼接。`%s` 只在真正输出时才格式化。

## 9. 安全

| 风险 | 措施 |
|---|---|
| API Key 泄露 | 全部走 `.env`，`.gitignore` 排除；代码里零硬编码 |
| 路径穿越 | `safe_filename()` 清洗上传文件名；`/ingest/batch` 限制目录在项目内 |
| 时序攻击 | `secrets.compare_digest()` 常量时间比较密钥 |
| 信息泄露 | 兜底异常处理不返回堆栈，只写服务端日志 |
| 容器逃逸 | Docker 里用非 root 用户运行 |
| 文件过大 | `MAX_FILE_SIZE_MB` 限制（默认 50MB），超出返回 413 |

## 10. 如果要上生产，还缺什么

诚实列出，也是面试时可以聊的「下一步」：

1. **认证升级**：目前是单 API Key，需要 JWT + 用户体系 + 行级权限
2. **向量库升级**：Chroma 单机 → Milvus/Qdrant（`VectorStore` 已做抽象）
